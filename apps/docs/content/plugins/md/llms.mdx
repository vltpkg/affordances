title: llms.txt and llms-full
description: An index of every page for agents, and the whole site's Markdown in one file, each from one route handler.
---

[`llms.txt`](https://llmstxt.org) is where agents look first: the site's name, a summary, and a link to every page's Markdown. `llms-full.txt` is every page's Markdown in one file. `@affordances/md` serves both, each from a route handler.

## Both files in two lines

Neither handler needs a page list. They list every page that needs no params: the ones `md()` found in `app/`, and on an Affordances site, the routes in its [index](/docs/reference/protocol) at `/.well-known/affordances.json`:

```ts title="app/llms.txt/route.ts"
export { GET } from '@affordances/md/next/llms'
```

```ts title="app/llms-full.txt/route.ts"
export { GET } from '@affordances/md/next/llms-full'
```

`llms.txt` then has:

- the site's name from the index, as its heading (or the host, without one);
- a line on reading any page as Markdown, linking `llms-full.txt`;
- a line saying the site is Affordances-enabled: how to ask a page for its graph, and where the site index is. An agent that starts at `llms.txt` learns it can act on the site, not just read it;
- a link to each page's Markdown, titled with the page's own title and described with its route's `description` from `state.ts` (written for agents), or else the page's meta description.

```md title="/llms.txt"
# Acme Store

> Studio goods in small runs.

Every page is also Markdown: add `.md` to its URL, or request it with `Accept: text/markdown`. For the full text in one file, see [llms-full.txt](https://acme.store/llms-full.txt).

This site is Affordances-enabled: request any page with `Accept: application/vnd.affordances+json` for its graph (what the page shows, and the actions you can call there, with their inputs). [/.well-known/affordances.json](https://acme.store/.well-known/affordances.json) lists every route and its actions.

## Pages

- [Home](https://acme.store/index.md): Every product: its lowest in-stock price, options, and whether it is in stock
- [Cart](https://acme.store/cart.md): The cart: items, quantities and subtotal
```

## Pages behind dynamic routes

A route like `/products/[slug]` has no single page, so it isn't listed on its own. Call the handlers yourself and name its pages; you're given the routes that need no params:

```ts title="app/llms.txt/route.ts"
import { createLlmsTxtHandler } from '@affordances/md/next'
import { products } from '@/lib/store'

export const GET = createLlmsTxtHandler({
  summary: 'Studio goods in small runs.',
  sections: (request, routes) => [
    { title: 'Pages', pages: routes },
    { title: 'Products', pages: products().map((p) => `/products/${p.slug}`) },
  ],
})
```

```ts title="app/llms-full.txt/route.ts"
import { createLlmsFullHandler } from '@affordances/md/next'
import { products } from '@/lib/store'

export const GET = createLlmsFullHandler({
  pages: (request, routes) => [...routes, ...products().map((p) => `/products/${p.slug}`)],
})
```

### A catch-all page

A docs site often renders every page through one `app/[...slug]/page.tsx`, so `routes` lists none of them. Neither handler reads your sitemap or `generateStaticParams`: on a site with many thousands of pages those lists have no bound, and a file that has to render every one of them would always run out of time. List the pages from your content source instead, in one module both handlers share. With fumadocs:

```ts title="lib/llms.ts"
import { source } from '@/lib/source'

// every docs page, in the sidebar's order
export const docsPages = () => source.getPages().map((page) => page.url)
```

```ts title="app/llms.txt/route.ts"
import { createLlmsTxtHandler } from '@affordances/md/next'
import { docsPages } from '@/lib/llms'

export const GET = createLlmsTxtHandler({
  sections: (request, routes) => [
    { title: 'Pages', pages: routes },
    { title: 'Docs', pages: docsPages() },
  ],
})
```

```ts title="app/llms-full.txt/route.ts"
import { createLlmsFullHandler } from '@affordances/md/next'
import { docsPages } from '@/lib/llms'

export const GET = createLlmsFullHandler({
  pages: (request, routes) => [...routes, ...docsPages()],
})
```

When `pages` already has each page's Markdown (a content layer that keeps it), give it as `{ url, title, markdown }` and nothing is rendered. Each page given as a path is rendered once per request of the file, so with many of them, cache the files ([`publicCache`](#how-the-files-are-made)) and raise `deadline` with the route's `maxDuration`.

## Prose sections

A section can say something as well as list pages: its `intro` is Markdown under its heading, before its pages, and a section with an `intro` and no `pages` is prose alone. Links in it, and in the top-level `intro`, are made absolute and point at your pages' Markdown twins, as page links are, since an agent reads `llms.txt` away from your site:

```ts title="app/llms.txt/route.ts"
import { createLlmsTxtHandler } from '@affordances/md/next'

export const GET = createLlmsTxtHandler({
  summary: 'Studio goods in small runs.',
  sections: (request, routes) => [
    {
      title: 'Ordering',
      intro: 'Orders ship in two days. See [shipping](/shipping) and [returns](/returns).',
    },
    { title: 'Pages', intro: 'Everything in the store.', pages: routes },
  ],
})
```

```md
## Ordering

Orders ship in two days. See [shipping](https://acme.store/shipping.md) and [returns](https://acme.store/returns.md).

## Pages

Everything in the store.

- [Home](https://acme.store/index.md): Every product, with its price
```

## Options

`createLlmsTxtHandler`:

| Option     | Type                                                          | Description                                                                                                                                                                                                                                                                                        |
| ---------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`    | `string`                                                      | The `#` heading. Defaults to the site index's `name`.                                                                                                                                                                                                                                              |
| `summary`  | `string`                                                      | The `>` summary under it.                                                                                                                                                                                                                                                                          |
| `note`     | `string \| false`                                             | Replaces what the plugin says after the summary: that every page is Markdown, where `llms-full.txt` is, and on an Affordances site how to read its graphs. Markdown, its links made absolute and twinned. `false` leaves it out.                                                                   |
| `intro`    | `string`                                                      | More Markdown after the note, before the page lists, such as how to use the site. Its links point at their twins.                                                                                                                                                                                  |
| `sections` | `(request, routes) => { title, intro?, pages?, sections? }[]` | The sections, each under a `##` heading: an `intro` in Markdown, then its pages, then its own `sections` under `###`, down to `######`. A page is a path, whose title and description are read from it, or `{ url, title, description }`. A section with nothing in it, at any depth, is left out. |
| `full`     | `string \| false`                                             | Where `llms-full.txt` is, to link it. Defaults to `/llms-full.txt`; `false` leaves the line out.                                                                                                                                                                                                   |

`createLlmsFullHandler` takes `pages: (request, routes) => …[]`, the pages in order, defaulting to the routes. A page is a path, rendered as `/page.md` is, or `{ url, title?, markdown }` with its Markdown given outright, a string or a function of the request. That one is never rendered or fetched, so a site with a data layer skips the HTML round trip. Its links are made absolute and point at their twins, as a rendered page's are, and it's headed `# Title (url)`, from its own first heading when there's no `title`. A `markdown` function that throws is a page that failed. `append: (request) => string | undefined`, as on `createMdHandler`, adds Markdown at the end of the file. Head each block `# Title (url)`, as the pages are:

```ts title="app/llms-full.txt/route.ts"
import { createLlmsFullHandler } from '@affordances/md/next'
import { changelog, packageMarkdown } from '@/lib/content'

export const GET = createLlmsFullHandler({
  pages: (request, routes) => [
    ...routes,
    { url: '/changelog', title: 'Changelog', markdown: changelog },
    { url: '/package/express', markdown: () => packageMarkdown('express') },
  ],
  append: () => '# Support (https://acme.store/support)\n\nEmail support@acme.store.',
})
```

Both also take the [Markdown handler's](/docs/plugins/md/caching#behind-a-proxy) `origin`, `timeout`, and `headers`, for the requests they make. A rendered page's Markdown is exactly what its Markdown route returns, so how each page renders (`maxBytes`, `linkTwins`, a page's own `append`, and `headers` for the page render itself) is configured on that route's `createMdHandler`. That fetch needs `md()`'s rewrites in `next.config`, or a `proxy.ts` that rewrites with `mdRewrite`.

A page given as a path is rendered the way `/page.md` is, to read its title and description. With many pages, give `{ url, title, description }` from your content source instead: nothing is rendered, and the file comes back faster. This site does that for its sidebar.

## How the files are made

- Each page is fetched at its `.md` twin (at its own URL with `Accept: text/markdown` on a [`literalMd`](/docs/plugins/md/setup#pages-whose-url-ends-in-md) route, where `x.md` may be a page of its own), through your rewrites and `proxy.ts` like any anonymous agent's request, so it matches what an agent reads one page at a time, a [`markdown.ts`](/docs/plugins/md/markdown-file) included. A page your proxy turns away (a redirect to log in) is left out.
- That request carries none of the caller's cookies, and each page renders in a request of its own: both files are the public site, even for a `markdown.ts` that reads `cookies()`.
- Both files are the public site, whoever asks. `pages`, `sections`, a page's `markdown`, `append` and the `headers` option get one request with none of the visitor's headers: no cookies, no `authorization`, no language. A request that carries a `cookie` or `authorization` still gets the public file, but its copy is `private, no-store`, since `cookies()` and `headers()` from `next/headers` read the real request, and so does anything they reach.
- They're the public view, so a page that only renders privately is left out of `llms-full.txt`, and `llms.txt` lists it by its path, with no title or description from that render. That's a page whose Markdown route rendered it with credentials (the route's own `headers` option, say), one that sets a cookie, or a `markdown.ts` `Response` marked private. A page Next sends as `private, no-store` only because it's dynamic is still in: rendered without credentials, it's the public view. If your Markdown route's `headers` option carries a service `cookie` or `authorization`, every page these files fetch renders with it, so `llms-full.txt` comes out with no pages; use a header that isn't a credential (such as `x-vercel-protection-bypass`) for that route instead.
- A `Set-Cookie` your `proxy.ts` adds to the response comes after the handler, which can't see it, and would go out on that publicly cached file. Don't refresh session cookies on `/llms.txt` and `/llms-full.txt` in your proxy (skip those paths in its matcher).
- In `llms-full.txt`, frontmatter is stripped, and each page is headed `# Title (url)`, with its title without the site's name (`Cart` for `Cart · Acme Store`). Its own first heading heads it instead when that's how the title starts, as it usually is, or when the title isn't the page's own: the site's name, or a title other pages share, such as a layout's on every page. A page whose first heading is something else (a finding, on a report) keeps it under the title.
- Each page is a full render on your own server, so they render a few at a time: `concurrency`, 8 by default, on either handler. `timeout` is each page's own, from when its request starts, and `deadline` is the whole file's, 25 seconds by default, under common serverless limits (Netlify's synchronous functions stop at 26). A page not rendered by then failed, as a timed-out one did. On a host that allows longer, raise it together with the route's `maxDuration`: `export const maxDuration = 60` and `createLlmsFullHandler({ deadline: 55_000 })`.
- A page with a [`markdown.ts`](/docs/plugins/md/markdown-file) default export is the fast path: when the default export answers, the page isn't rendered, here as for its twin, while any other page costs a full render and conversion. A page given as `{ url, markdown }` in `llms-full.txt`, or a link given as `{ url, title, description }` in `llms.txt`, is never rendered at all.
- A page that failed (a timeout, the `deadline`, a `5xx`, `408` or `429`, a fetch error, or a page still loading after its `timeout`) may render next time, so a file missing it is never cached:
  - `llms-full.txt` answers `503`, with `Cache-Control: no-store` and `Retry-After`;
  - `llms.txt` still links it, by its path, so its links are all there and right, and it stays cacheable.

  Both say how many failed with an `x-affordances-md-dropped` header. They never list them, since they're public and the list could name a private page.

- A page that isn't part of the public site is left out by design, and the file stays cacheable: a redirect, any other `4xx` (a `404`, a gate's `401`), a response that isn't Markdown, a private render, or a page with a boundary that caught an error (`x-affordances-md-uncached: error`), which a retry wouldn't change. `llms.txt` still links it by its path. In development the server logs each page left out, failed or not, and why; a private render is logged as an error, since it's usually a page you meant to be public.
- Without an Affordances index (`@affordances/md` on its own), the pages come from `app/` alone, and `llms.txt` leaves out the Affordances line.
- Both are cached publicly for an hour (`s-maxage=3600`). `publicCache` on either handler sets another time, with the same values as [`markdown.ts`'s](/docs/plugins/md/caching): a `cacheLife` profile or `{ revalidate, expire? }` in seconds, which gives the header Next sends for a page cached that long. `false` means never:

  ```ts title="app/llms-full.txt/route.ts"
  import { createLlmsFullHandler } from '@affordances/md/next'

  export const GET = createLlmsFullHandler({ publicCache: 'hours' }) // s-maxage=3600, stale-while-revalidate=82800
  ```

  A `503`, or a file rendered with credentials, is never cached, whatever it says.

Both render by requesting the site's own pages, so they run at request time. They read the request first, which keeps Next from prerendering them during the build, when no server is running.
