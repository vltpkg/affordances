---
title: Caching and privacy
description: The Markdown is the page that caller would see, and it's only cached when the page is public.
---

The handler forwards the caller's `cookie`, `authorization`, and `accept-language` headers, so a signed-in agent gets the page that person would see. Everything about that response stays personal:

- With a cookie or bearer token, or when the page is `private` or `no-store`, or sets a cookie, the Markdown is sent with `Cache-Control: private, no-store`.
- Markdown served at a URL that also serves the page's HTML is `private, no-store` too, whatever it is: converted Markdown, a redirect, or what a `markdown.ts` returns. That's the page's own URL asked for with `Accept: text/markdown`, and a `literalMd` page whose own URL ends in `.md`. A cache that ignores `Vary` (Cloudflare's Cache Everything does) would serve one for the other. The `.md` twin URL is its own, so it keeps the page's `Cache-Control`.
- A page with a boundary that caught an error (its `error.tsx`, or a `<Suspense>` child that threw) is missing that part, so its Markdown is `private, no-store` with `x-affordances-md-error: 1`, whatever the page's own `Cache-Control` or `publicCache` says.
- Otherwise it keeps the page's own `Cache-Control`.
- Converted Markdown has `Vary: Accept` (and `Accept-Language` too when the page varies on it, since the handler forwards the caller's language), `X-Affordances-Tokens` with an estimate of its length in tokens, and a `Link` to the canonical page when it has one.

A response the handler passes on rather than converts (a file in `public/`, JSON, a client navigation's RSC payload, a `.md`-named page's HTML) keeps the page's own headers, except that it's `private, no-store` whenever the request carried a cookie or an `authorization` header, and a cookie set in answer to the `headers` option's credentials never goes out.

The status code is the page's. A redirect to the same site stays in Markdown (to the target's `.md`), varies on `Accept`, and is cached as the page would be (private when it's credentialed, private, or sets a cookie). One to another origin is passed on as it came, never followed: the agent decides whether to follow it. That includes a `redirect()` a page calls after its shell has streamed, which Next can only send as a `200` that refreshes the browser: the handler answers it with a real `307` (`308` for `permanentRedirect()`). A `notFound()`, `forbidden()` or `unauthorized()` after the shell is the same: Next sends a `200`, and the handler answers `404`, `403` or `401`, `private, no-store`. A page that is still streaming after 10 seconds is converted as far as it got, marked partial and never cached ([slow boundaries](/docs/plugins/md/conversion#slow-boundaries)); one that sends nothing by then answers `504`, and one larger than 6 MiB answers `413`, saying how to raise `maxBytes`.

## Caching public Markdown

Markdown from a `markdown.ts` (a default export or its slots) is `private, no-store`, since it read data with whatever the request carried. So is a page Next renders dynamically, which it always sends as `private, no-store`. When a route's Markdown is public, say so in its `markdown.ts`, and a CDN can keep it:

```ts title="app/package/[pkg]/markdown.ts"
export const publicCache = 'hours'
```

`publicCache` is a [`cacheLife`](https://nextjs.org/docs/app/api-reference/functions/cacheLife) profile, Next's own (`'seconds'`, `'minutes'`, `'hours'`, `'days'`, `'weeks'`, `'max'`, `'default'`) or one from your `next.config`'s `cacheLife`, or the same times in seconds: `{ revalidate: 300, expire: 86_400 }`. The `.md` gets the `Cache-Control` Next sends for a page cached with that profile: `'hours'` is `s-maxage=3600, stale-while-revalidate=82800`. It works for every kind of route:

```ts
// slots: one line next to them
export const slots = {
  readme: async ({ params }) => readme(params.pkg),
} satisfies Slots<'/package/[pkg]'>
export const publicCache = 'hours'

// a default export
export default (async ({ params }) => pkgMarkdown(params.pkg)) satisfies Markdown<'/package/[pkg]'>
export const publicCache = { revalidate: 300, expire: 86_400 }

// a page converted from its HTML: a markdown.ts with only this
export const publicCache = 'days'
```

It applies only to the anonymous view of the `.md` URL. The response is public only when all of these hold, and otherwise it's exactly what it would be without `publicCache`:

- the request has no `cookie` and no `authorization`, and the handler's `headers` option adds neither;
- it's the `.md` URL, not the page's own URL asked for with `Accept: text/markdown`, which stays private since some CDN modes ignore `Vary`;
- the answer is a `200`, the page finished streaming before the timeout, and no boundary in it caught an error;
- the page didn't set a cookie. A page that sets one for an anonymous visitor (a session, an auth handshake) stays private, and in development the server says which cookie.

A `Response` your default export returns keeps its own `Cache-Control`, as before. A name that isn't a profile, or an object with another field (`'hourz'`, `{ revalidat: 300 }`), fails `tsc` (and `next build`), named in the route's `markdown.ts` with Next's closest profile, against Next's profiles and your `next.config`'s. In development the server also says which file and what it can be. Until it's fixed, the route isn't cached.

**Only the anonymous view is ever stored.** Credentials make a response `private, no-store`, so no one is served someone else's Markdown. But a CDN that doesn't key on cookies (Vercel's and Cloudflare's don't) may serve that public view to a signed-in agent. If signed-in agents need their own view of a route, don't opt it in, or skip the CDN cache when the session cookie is present (a Cloudflare Cache Rule, say). `publicCache` doesn't send `Vary: Cookie`: Vercel doesn't cache a response that varies on cookies, and Cloudflare ignores it.

**Only `cookie` and `authorization` count as credentials.** A site that authenticates with a header of its own, such as `x-api-key`, or with a token in the query string (`?token=`, `?api_key=`), must not opt in: a request carrying only that would get, and a CDN could store, the view it unlocks. The same goes for any other request header a default export or fill reads (`user-agent`, `x-forwarded-for`): the stored view would depend on something the cache key doesn't include.

**A public `.md` is one view, the same for every visitor.** A CDN keys it on its URL alone: Cloudflare ignores `Vary`, and Vercel splits its cache on each value. So for a request whose answer can be public (no credentials, the `.md` URL), the handler renders the page with none of the visitor's headers (no language, user agent or country), and your default export, fills and `append` get a `request` of the URL with none of them either; `request.url` and `nextUrl` still carry the host. Next's `headers()` from `next/headers` still sees the visitor's own, so don't read it on an opted-in route. A site in several languages gets one cached view per URL: put the language in the URL (`/fr/…`) to cache each. In development, an opted-in route whose page varies on `Accept-Language` says so. A signed-in or `Accept` request, which stays private, is the visitor's own.

**A cached `.md` stays until its time runs out.** A page that becomes private, or a package that's unpublished, is still served from the CDN until its `expire` (its `revalidate` plus the `stale-while-revalidate` after it). Choose lengths with that in mind, or purge your CDN's copy when it changes. The data behind it can stay fresh on its own: `'use cache'` with `cacheLife` and `cacheTag` works in a default export and in a fill, and `revalidateTag` refreshes it on publish:

```ts title="app/package/[pkg]/markdown.ts"
import { cacheLife, cacheTag } from 'next/cache'

async function readme(pkg: string) {
  'use cache'
  cacheLife('hours')
  cacheTag(`pkg:${pkg}`)
  return fetchReadme(pkg)
}

export const slots = {
  readme: ({ params }) => readme(params.pkg),
} satisfies Slots<'/package/[pkg]'>
export const publicCache = 'hours'

// and where a package is published: revalidateTag(`pkg:${name}`, 'max')
```

`revalidateTag` refreshes the data, not a CDN's copy of the `.md`, which lasts its own time.

## Behind a proxy

The handler fetches pages from the request's own origin. When a proxy changes it, set `AFFORDANCES_MD_ORIGIN`, or build the handler with options:

```ts title="app/api/affordances/md/[[...path]]/route.ts"
import { createMdHandler } from '@affordances/md/next'

export const GET = createMdHandler({ origin: 'http://localhost:3000', timeout: 5000 })
```

| Option     | Default       | Description                                                          |
| ---------- | ------------- | -------------------------------------------------------------------- |
| `origin`   | the request's | Where to fetch pages from                                            |
| `timeout`  | `10000`       | Milliseconds before converting what has streamed, or answering `504` |
| `maxBytes` | 6 MiB         | The largest page HTML it converts, or answers `413`                  |
| `headers`  | none          | More headers on the page fetch: an object, or `(request) => headers` |
| `append`   | none          | More Markdown after the page's, such as an actions summary           |

`headers` are set after the forwarded ones, for a request the render needs that the caller didn't send, such as `x-vercel-protection-bypass` on a protected preview. A `cookie` or `authorization` here applies only to a request that sent neither: a signed-in person's Markdown is rendered with their own credentials alone, never the service account's, so it never shows more than they could see, while an anonymous request renders with the service's. It's all or nothing, so a visitor carrying any cookie, even an unrelated one (analytics, consent), is rendered without the option's credentials, as if there were none; it fails closed. On a protected preview whose bypass rides on a `cookie` or `authorization` here, that visitor's Markdown may be the protection or login page rather than the content; a bypass in its own header, such as `x-vercel-protection-bypass`, isn't a credential and always applies, so use one of those for a protected preview. Either way the Markdown is private, and a cookie set in answer to the service's never goes out. Put a service account's credentials in `cookie` or `authorization`: the handler can't tell any other header (an `x-api-key`) is one, so it wouldn't keep a person's request from using it, nor treat the response as theirs. The `llms.txt` and `llms-full.txt` handlers take it too: they render anonymously, so its credentials always apply there, and the files are then `private, no-store`.

A path that would leave the origin, such as one starting with `//host`, answers `400` before anything is fetched, so the caller's credentials only go to your own site.
